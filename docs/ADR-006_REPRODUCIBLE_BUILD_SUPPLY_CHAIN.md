# ADR-006 — Reproducible build and sealed supply chain

- **Status:** Accepted
- **Date:** 2026-07-12
- **Scope:** FloorPlan Stage 1, Compliance Engine, Docker/Compose and CI

## Context

The Phase 5 source tree could run its test suite, but production builds still had non-deterministic inputs:

- open dependency ranges resolved differently over time;
- CUDA Torch wheels and model weights lived outside the source archive without one uniform sealing workflow;
- base images were referenced by mutable tags;
- the Stage 1 CUDA image assumed `python3.11` existed in Ubuntu 22.04 repositories;
- the compliance image downloaded Hugging Face models during build;
- Stage 1 and the engine used different build contexts;
- repeated native IFC tests could hang during interpreter cleanup even after JUnit was complete;
- no release SBOM described locked Python packages and external artifacts.

## Decision

### 1. Authoritative hashed dependency locks

Production and CI use five locks generated by `uv==0.8.4` for Python 3.11 and Linux x86_64:

- `requirements/stage1-runtime.lock`
- `requirements/stage1-ml-overlay.lock`
- `requirements/baseline.lock`
- `compliance-engine/requirements/runtime.lock`
- `compliance-engine/requirements/ml-overlay.lock`

Every package in those files has one or more SHA-256 hashes. Docker installs runtime locks with `pip --require-hashes`.

CUDA Torch is not resolved from PyPI. The operator-provided `torch` and `torchvision` wheels are installed first with `--no-deps`. Packages that require Torch are installed from small no-dependency overlay locks. This prevents a resolver from introducing another Torch/CUDA distribution.

### 2. Immutable base inputs

The build pins CUDA, Python and Redis images by digest. Stage 1 builds CPython 3.11.15 from the official source tarball inside the CUDA builder image and verifies the tarball SHA-256 before extraction. This avoids relying on an unavailable Ubuntu 22.04 `python3.11` package.

The Compose contract is `linux/amd64`, matching the ABI of the external CUDA wheels.

### 3. Sealed external artifacts

`artifacts-manifest.json` is the authority for external wheels, detector weights, the regulation corpus and offline compliance-model directories. A strict release requires size, file count where applicable, and SHA-256/tree SHA-256 to match the manifest.

The source release intentionally excludes large external artifacts. The operator copies them into their documented paths and runs:

```bash
python3.11 scripts/preflight.py \
  --mode full-pipeline \
  --refresh-manifest \
  --strict \
  --artifacts-only
```

Docker builders verify the sealed Torch wheels before installing them.

### 4. Offline model runtime

Compliance images do not download embedding or reranker models at build time. Hugging Face cache and reranker directories are mounted read-only and runtime is configured with:

```text
HF_HUB_OFFLINE=1
TRANSFORMERS_OFFLINE=1
```

### 5. Deterministic SBOMs

CycloneDX 1.5 SBOMs are generated from lock files and the artifact manifest. Their serial numbers are derived from source hashes and no wall-clock timestamp is inserted, so identical inputs produce byte-identical SBOM files.

### 6. Process-isolated native tests

Each Stage 1 test module runs in its own process group. Ordinary modules run concurrently; provenance/IfcOpenShell bridge shards run serially after them. JUnit is authoritative only when it is complete and records zero failures/errors. A process may be killed after JUnit completion solely to terminate a native cleanup hang, and this condition is recorded.

### 7. CI separation

CI has four boundaries:

1. quality, contracts, tests, acceptance and SBOM;
2. daemon-free Compose expansion and container contract validation;
3. scheduled lock re-resolution proof;
4. optional self-hosted strict no-cache Docker build with provisioned external artifacts.

A strict image build is not claimed unless the fourth boundary runs successfully.

## Consequences

### Positive

- dependency resolution is reviewable and repeatable;
- mutable image tags no longer determine production content;
- external artifacts fail closed when unsealed or changed;
- build-time network access is reduced and model downloads are eliminated;
- Docker and CI use the same dependency contract;
- native cleanup behaviour cannot silently invalidate or hang the whole test suite;
- release contents have machine-readable SBOM, provenance and checksums.

### Trade-offs

- lock regeneration requires network access and the pinned `uv` version;
- Stage 1 builds CPython from source, increasing first-build duration;
- strict Docker build cannot run until the external wheels and model directories are provisioned and sealed;
- PaddleOCR/pdf2docx metadata requires three OpenCV distribution names. All are aligned to exactly 4.6.0.66 to avoid mixed cv2 binary versions, but the upstream packaging overlap remains documented.

## Rejected alternatives

- **Unpinned ranges in production:** rejected because new releases could change a clean build without a source change.
- **Download models during Docker build:** rejected because it is mutable, network-dependent and hard to audit.
- **Resolve Torch from PyPI:** rejected because it can pull a different CUDA stack than the operator-provided cu118 wheels.
- **Install Python 3.11 from default Ubuntu 22.04 apt repositories:** rejected because that package is not a reliable base-image contract.
- **Treat process timeout as a passed test:** rejected. A pass requires a complete JUnit report with zero failures/errors.
